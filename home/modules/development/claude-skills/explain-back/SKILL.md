# explain-back — 理解を外注しないための逆質問

AIに実装させると、動くコードは増えるが**説明できないコード**も増える。技術負債と同時に
たまるこの「理解負債」を見つけるためのSkill。

やることは1つ。**説明する側と される側を逆にする。** いつもは Claude が「こう実装しました」
と説明するが、ここでは Claude が質問し、ユーザーが答える。

参考：<https://zenn.dev/avaintelligence/articles/dont-outsource-understanding-to-ai>

## 使うタイミング

- PRをマージした直後（記憶が新しいうちに穴を見つける）
- その実装について文章を書く前（論文の章、記事、READMEなど）
- 人に説明する予定がある前（発表、レビュー、引き継ぎ）

逆に、使わなくていい場面もある。定型的な設定変更、依存の更新、他人のコードをそのまま
使った箇所。**判断が入っていないところに理解負債は生まれない。**

## 手順

### 1. 対象を決める

引数があればそれ。無ければ直近のマージ済みPR、または現在のブランチの差分。

```sh
git log --oneline -5
git diff main...HEAD --stat
```

### 2. 「判断」を抽出する

差分を読み、**「なぜAではなくBにしたのか」が存在する箇所**だけを拾う。目安は3〜7個。

判断がある例：
- 閾値・上限・既定値を選んだ（なぜその数字か）
- エラー時に「止める」か「続ける」かを決めた
- データ構造や保存形式を選んだ
- 何かを「やらない」と決めた（スコープを切った）
- トレードオフを片方に倒した（安全側／速度側／単純さ）

判断が無い例（聞かない）：
- 言語やライブラリの定型的な書き方
- テストのアサーション1行1行
- import の並び、命名の細部

### 3. 質問する

**3〜5問に絞る。** 全部聞くと疲れて形骸化する。抽出した判断のうち、
**間違えたときの影響が大きい順**に選ぶ。

質問の作り方：

| やること | やらないこと |
| --- | --- |
| 「**なぜ**そうしたか」を聞く | 「何をしているか」を聞く（コードを読めば分かる） |
| 何も見ずに答えられる形で聞く | 選択肢を出す（再認は再生より簡単で、理解の証拠にならない） |
| 1問ずつ出す | まとめて5問出す（後半が雑になる） |
| 「もし逆にしたら何が起きる？」と聞く | 答えを匂わせる前置きを付ける |

良い質問の例：

> レート制限の残量判定を、実際に使った量ではなく「最悪ケース」で見積もっています。
> なぜ実測ではだめなんでしょう。実測にすると何が起きますか。

> pre-commitフックがあるのに、CIにも同じ秘密スキャンを置きました。二重にした理由は何ですか。

悪い質問の例：

> 残量判定の関数は何をしていますか。 ← what を聞いている
> 判定は (a)実測 (b)最悪ケース のどちらですか。 ← 選択肢を出している
> 呼ぶ前に判定するのは事故を防ぐためですが、なぜだと思いますか。 ← 答えを言っている

### 4. 答え合わせ

- **答えられた** → 「そこは理解できている」と短く確認して次へ。褒めちぎらない
- **部分的** → 足りない部分だけ補う。全部を再説明しない
- **答えられない／間違い** → **そこだけ**解説する。併せて
  **「これを理解していないと、この先どこで困るか」**を1文で言う。理由が分からないと、
  次も同じ場所で詰まる

答えを聞く前に解説を始めないこと。待つ。

### 5. 記録する

答えられなかった項目を残す。

- プロジェクトに作業ログや引き継ぎドキュメントがあれば、そこへ「理解負債」として1行
- 無ければその場でユーザーに提示し、どこに残すか聞く

記録した項目は**次回も聞く**。埋まったら消す。

### 6. まとめて出す

```
## explain-back 結果（対象: PR #13 object constancy）

理解できている
- 値マッチで安定IDを振る方針（なぜトレース側にIDが無いのかまで説明できた）

理解負債として残る
- CSS transform を使った理由（他の実装手段との比較が説明できなかった）
  → この実装について文章を書くなら、先に埋めておく必要がある
```

## 注意

- **これはテストではない。** 点数を付けない、成績を出さない。目的は穴の発見であって評価ではない
- **答えられないことを責めない。** AIに書かせた以上、理解負債が出るのは当然。見つけるためのSkill
- **Claudeが自分で書いたコードを対象にする場合、質問は自分への監査になる。**
  自分の実装判断を正当化する方向に質問を歪めないこと。「ここは説明が足りなかった」と
  分かったら、それはコード側かドキュメント側の問題でもある
